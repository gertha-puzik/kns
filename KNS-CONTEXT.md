# KNS Paint — контекст проекта одним файлом (для любой ИИ)

**Как использовать:** приложи этот файл целиком в новый диалог с любой моделью или агентом. Обновлять после крупных изменений. Последнее обновление: 2026-11-14 — репозиторий сведён к одному продукту, KNS Paint.

## 1. Что это за проект

**KNS Paint** — браузерный редактор окрасов: игрок красит кота кистью поверх скетча (300×200, прозрачный фон, краска клипнута по силуэту) и выгружает PNG для игры **coop-field** заказчицы (https://abnocw.phainonsmilk.ru, репо github.com/gertha-puzik/coop-field). Решение заказчицы от 2026-11-14: из всех направлений KNS продуктом остаётся только Paint.

- Сайт: **https://paint.phainonsmilk.ru** (корень = редактор). Прежние адреса `kns.phainonsmilk.ru` и `kns.miew.ru` должны вести 301 на него; vhost, DNS и сертификат заводит заказчица, агенты на VPS не ходят.
- Каталог на VPS прежний (см. `.github/workflows/deploy.yml`), деплой — CI (rsync) при пуше в `main`.
- `/paint-demo/` — редирект на корень с сохранением `?query` и `#hash`, чтобы старые ссылки и диплинки работали.
- В coop-field лежит своя копия редактора (`public/paint-demo/`, с `game-bridge.js`). Её сверяют и обновляют отдельным PR в coop-field; этот репозиторий её не трогает.
- Репозиторий публичный, видимость не менять.

## 5. Конвенции работы

1. **Законченный проверенный результат, не план**: каждая фича проверяется живьём (браузерный зонд canvas: пиксельные диффы и счётчики), цифры приёмки в отчёте.
2. Женский род, по-русски, коротко; деструктивные команды — только после явного подтверждения; состояние внешних систем (push/deploy) — оставлять последнее слово за заказчицей, если она не дала отмашку на автоматизацию (обычно дала).
3. **Git: ветки + PR** (введено 2026-11-05 — параллельные агенты в одной ветке перезатирали код друг друга; подтверждено заказчицей; проверено: worktree-механика рабочая):
   - `main` — единственная ветка-деплоя (push в неё → CI → rsync → paint.phainonsmilk.ru). Агенты НЕ коммитят и НЕ пушат в `main` напрямую; любое изменение (код, досье) идёт через PR из ветки. Соло-исключений нет: сторож main-guard (`.github/workflows/main-guard.yml`) откатывает любой прямой пуш в main реверт-коммитом + alarm-issue, не разбирая, код это или одно досье (легитимное — merge-коммиты, серверные мерджи PR, реверты сторожа); каждый PR перед мерджем проходит линт бот-гейта «KNS QC» (`.github/workflows/kns-qc.yml`: сломанные JSON/JS-скобки, CJK-мусор, шаблон `act{act}`, инвариант `assetRoot=""`) — красный QC = мердж не открывать.
   - Одна задача = одна ветка от свежего `origin/main`: `git fetch origin && git switch -c <тип>/<slug> origin/main` (типы: `feat`/`fix`/`chore`/`agent`; slug уникален для задачи; правки KNS-CONTEXT.md техническими агентами — канон один, зеркала (репо + kns-clone) синхронизировать при правках).
   - Параллельные задачи НИКОГДА не работают в одной рабочей копии — каждой свой worktree: `git -C kns-repo worktree add ../kns-wt/<slug> -b <тип>/<slug> origin/main`. Оркестратор выдаёт каждому субагенту его путь и имя ветки в goal; субагент работает только внутри своего worktree. Основная копия `kns-repo/` остаётся чистой, на `main`. Пуш ветки НЕ триггерит деплой — CI срабатывает только на push в `main`.
   - Перед открытием PR: `git fetch origin && git rebase origin/main`, конфликты решает автор ветки. Force-push — только в собственную ветку (после rebase), в `main` — никогда.
   - PR = одна задача, без посторонних изменений; в описании — что сделано и как проверять (зонды, цифры приёмки). Мерж — merge commit (НЕ squash), чтобы сохранить сообщения ветки.
   - Открывший PR агент НЕ мержит его сам: мерж в `main` = деплой на прод, последнее слово за заказчицей (или явная отмашка в задаче). Не мержить PR, конфликтующий с другой открытой веткой, без её rebase-проверки.
   - После мерджа: `git worktree remove` + удалить ветку (локально и на origin), в `kns-repo/` — `git pull --ff-only`; CI ждать прогон с headSha == HEAD (не предыдущий зелёный), затем прод-проверка curl + js-зонд.
